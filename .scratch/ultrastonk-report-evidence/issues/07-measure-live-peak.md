# 07: Measure live peak load and headroom

**What to build:** A report writer can tell whether the running pipeline kept up with the recorded peak and had headroom, independently of the full-week reference result.

**Blocked by:** 02 - Profile the official week and identify the real peak; 05 - Prove capture-paced End-to-end measurement.

**Status:** resolved

- [x] Run repeats at 1x capture-time pacing on the same peak slice, preserving exchange mix and burst order; ware state labelled, and every attempt including failures and invalid runs recorded. Reduced scope: one valid repetition only, cold and 1.25x dropped by team decision.
- [x] Show achieved pacing, expected and delivered counts by subscription, stage backlog, p50/p95/p99 and sample sizes, restarts/OOMs, and drain. Judge keeping up by correct delivery and no sustained backlog growth, not by eventual parity. Kafka broker and gateway consumer-group lag could not be collected and are recorded as missing evidence.
- [x] Report separate latency distributions for trade enqueue to WebSocket and estimated window eligibility to advisory receipt. Distinguish checkpoint-gated Kafka visibility from event-time window finalization.
- [x] Compare live query results to independent complete-input truth with verified pre-roll; report policy-related deviations separately from transport loss and identify missing evidence. No full-week extrapolation is claimed.

## Comments

- **Preparation landed (2026-11-23, coordinator).** The harness is `benchmarks/peak_slice.py` (peak slice carved from ticket 02's verified fixture, burst order preserved, with pre-roll and trailing segments and the emitter's non-zero/disjoint offset check; the measured segment reproduces the fixture's 1,223,873 rows and exchange mix or fails closed) and `benchmarks/live_peak.py` (run-plan builder, isolation-compliant Compose environment, per-run collection and evaluation, oracle comparison, ledger, checkpoint-cadence record). Committed as `091c672` and merged into `integration/report-evidence` (`79b283c`); unit tests included and the benchmark suite passes there (185 tests).
- **Pre-registered plan:** warm state by default with a forced-cold variant, headline conditions at `SPEED_MULTIPLIER` 1x and 1.25x, three valid repeats each, failures and invalid runs kept in the ledger. Pre-roll 300 s (one full 5-minute window, so EMA and watermark enter the peak non-zero) and trailing 180 s (past the last touched window's close plus the 5 s disorder budget so it finalises naturally), both flag-adjustable.
- **Scored phase held.** At this point the full-week reference replay occupied the host. Assumptions to verify in the scored phase: `FLINK_BOUNDED_REPLAY=false` (live pacing, not preload-and-process); live advisory p99 reported *inconclusive* below 20 samples; oracle run with the emitter's `Europe/Berlin` event zone. The peak run must not be extrapolated to full-week capture order.
- **Downscaled by team decision (2026-11-23).** To finish the programme within roughly two hours of machine time, the scored phase runs 1x capture pace with warm state only (the 1.25x condition and the cold variant are dropped), pre-roll 120 s and trailing 90 s, and one or two repeats decided by measured run cost, inside a hard 40-minute cap. The measured 5-minute peak segment, achieved-pacing check, delivered-versus-expected counts, backlog, tails with sample sizes, drain, oracle comparison with the policy/transport split and the "inconclusive" rule for sparse advisory signals are all retained. Reduced repeats lower confidence, and the report must say so; the run is started by the coordinator as a background task because the owning session requires a direct user go-ahead for scored load.
- **Result and acceptance mapping (2026-11-23).** One warm, live 1x repetition offered 1,914,978 rows in capture-time order, including a measured segment of 1,223,873 rows. Achieved pacing was **0.99991** (35 ms max lag). Delivery was exact: **195,061 price records expected = committed = WebSocket**. Trade enqueue to WebSocket was p50 **5,060 ms**, p95 **9,063 ms**, p99 **9,225 ms** (n=195,061). Kafka committed observation was already **9,206 ms p99**; the committed-reader-to-WebSocket observation gap was **134 ms p99**. Prices emit without waiting for a watermark. The exactly-once sink and 10 s checkpoints explain why checkpoint-gated visibility is the leading contributor. The separate advisory series starts at estimated eligibility, not at actual timer firing (p99 **241,126 ms**, n=3,154). See [stage timings and interpretation](../../../docs/live-peak.md#latency-p50p95p99-with-sample-sizes-two-paths-reported-independently). Drain was 7.08 s, with no container restarts or OOM kills. The oracle comparison found 3,341 missing final-window keys: policy 3,309 / transport 18 / unexplained 14.
- **Gaps recorded, not hidden.** Kafka broker lag and gateway consumer-group lag were not collected (`consumer_lag: {}`); the Flink input-minus-output count is not a queue-depth measurement. Only one repetition ran, at 1x and warm, finishing 1–2 minutes over its 40-minute cap.
- **Harness defects found and fixed, committed with the evidence.** `peak_slice.py` gained a documented `--reorder capture` mode (the raw physical order puts the first in-range row after the measured start, so the tool previously failed closed with `ValueError: emitter offsets do not place the measured start in the measured segment`); `live_peak.py` gained `--pacings` and corrected `GATEWAY_HISTORY_LIMIT` from 0 to 1 (0 crash-looped the gateway in the first attempt); `capture_pilot.py`'s `window_check` was quadratic in windows × rows and was replaced by an equivalent suffix-min index. The measured numbers depend on the first two changes, so they are committed rather than left as working-tree edits. Evidence: `benchmarks/evidence/live-peak/` (`summary.json`, `comparison-warm-1x-r1.json`, the classification split, `run-plan.json`, `ledger.json`, pacing and limits artifacts, the slice manifest and `blocked.json`) and `docs/live-peak.md`; the slice CSV, per-run raw JSON and committed-record dump stay outside Git by design.
