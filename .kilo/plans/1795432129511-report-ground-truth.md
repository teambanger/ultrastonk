# Ultrastonk report ground-truth plan

## Deliverable and scope

Build a reproducible evidence pack that a teammate can use to write the 4–5 page ACM report without guessing, rerunning the week, or inventing results. Cover all eight Exceptional criteria and both teamwork points in `docs/Evaluation_Criteria_26.pdf`; use the course project brief (§§3–4) as the query and submission specification. Targets below are project acceptance goals, not official grade thresholds. Do not write the report itself in this phase. New HA infrastructure, GPU work, and a broad chaos campaign are out of scope.

**Current baseline:** `de74872` adds resource profiles and measurement. Flink emits prices and EMA pairs, not live advisories; the gateway already accepts BUY/SELL. `verify.py` and operator tests validate controlled scenarios, not the entire week. The synthetic matrix checks price correctness and WebSocket/Kafka parity but not independent full-scale query correctness. The `c411a7c36444` smoke runs delivered all measured prices after drain at 5,000 originals/s offered; neither sustained that load. Existing standalone gateway measurements bypass Flink. The bounded historical overlay preloads Kafka and is not evidence of live latency. The default 10 s checkpoint cadence can dominate read-committed visibility and must not be ignored in a 1 s latency target.

## Execution order and exit evidence

**Critical path:** Start dataset acquisition/profile and the hand-calculated Query 2 fixture in parallel. The reviewed semantic contract unblocks the independent oracle and the live operator change. Require a passing slice through Flink, committed Kafka, and the comparator before the full week; require a pacing/clock check before live peak runs. Run peak and scaling trials on the measured host without overlapping the full-week job. If resources are tight, prioritize the exact week comparison, real-peak runs, a two-point worker/resource comparison, and one creative comparison over broader sweeps or new dashboards. Label any unrun dimensions as gaps.

1. **Establish data provenance, environment, and ownership.** Locate or obtain all seven official Nov 8–14, 2021 CSVs using the [Zenodo file manifest](https://zenodo.org/api/records/6382482/files) (DOI `10.5281/zenodo.6382482`, seven files, 24,874,180,296 bytes). `scripts/download_src_data.sh` currently fetches only Nov 12, so do not treat invoking it as acquiring the week. Reuse verified local files if present; compare byte sizes and provider MD5, record local SHA-256, ordered paths, version/license, and exact counted rows. Separately preflight the data filesystem and Docker's Kafka/checkpoint storage; measure bytes per row/output on a slice and budget for reference preprocessing if needed. Keep inputs read-only, run in unique Compose projects with fresh topics/groups, and retain artifacts before cleaning only the owned project. Record owners and cross-reviewers for semantics/oracle, experiments, and report evidence. Create the evidence index at kickoff and register every scored attempt, including failures.

2. **Profile the entire dataset and freeze the semantic contract.** Extend the analysis in `experiments/01_source_data_analysis/` to scan all seven files in chunks with no prefix cap. Produce `dataset-manifest.json`, `dataset-profile.csv`, and plot data: rows, price/quote/housekeeping/invalid categories and metadata availability per day, exchange and security type; symbol counts, ranked frequencies and top-1/top-10 shares; 1 s microbursts and rolling 5-minute rates for raw rows and trades; arrival/event time differences and timestamp fallback counts. Avoid assigning quote-only rows a trade count; document overlapping fields versus exclusive row dispositions. Select the highest **raw-row** rolling 5-minute arrival interval across concurrent FR/NL/ETR and record its timestamps, counts, exchange mix, and initial-state warmup; preserve actual subsecond arrivals and record how missing arrival timestamps are handled. Compare candidate peak selections if raw-row and trade peaks differ substantially, rather than silently substituting one. Inspect `DataLoader.java` against actual columns and the brief: trading date/time preference versus system fallbacks and time zones, retained `last` values versus actual new trades, fractional-second truncation, and publisher pacing. Agree and record trade eligibility, timestamp/tie rules, symbol identity, five-minute midnight alignment, empty windows, dedup and late-data semantics, and final flush. Where the brief is ambiguous, document an interpretation and its measured impact; don't redefine the reference to match Flink output. Exit with a reviewed spec, input accounting, and a reproducible peak fixture definition.

3. **Implement and verify live Query 2 and independent truth.** In `flink/.../PriceIndicators.java` and the output contract, emit at most one advisory per finalized nonempty symbol window from the prior and current EMA pair: BUY for previous fast-minus-slow <= 0 and current > 0; SELL for previous >= 0 and current < 0. Start both EMA states at zero; use the existing keyed/checkpointed path and publish through Kafka before WebSocket delivery. Preserve the closing-tick event timestamp and four-field output contract unless the fixture demonstrates a need for a separate window identifier; document how to derive the window key and join the two EMA values for presentation. Create a separate batch oracle starting from raw CSV, not production parsers, operators, or observed outputs. Use a disk-backed/chunked aggregation by `(symbol, window)` to select closes with a stable tie key, then compute chronological EMA pairs and advisories. Review it against manually calculated fixture outputs; verify first positive divergence, prior equality, no repeated advisory, ties, empty windows, late arrivals, symbol isolation, checkpoint/timer restore, and final-window flush. Freeze the numeric tolerance (`abs_tol=1e-9, rel_tol=1e-9`); require exact advisory directions/keys and zero missing, extra, duplicate, or out-of-tolerance outputs for the reference mode. Keep all-valid-trades event-time truth separate from policy-aware expectations. For deterministic policy tests derive expected admission from a prescribed arrival/watermark schedule, not from Flink's own admit/drop outcome. Exercise Kafka-to-WebSocket delivery with overlapping/disjoint subscriptions, both advisory directions, and a non-subscribed symbol. Assert live messages separately from history. Exit with a checked fixture, comparator, and real browser capture from Query 2.

4. **Validate measurement on a slice before using the whole week.** Reuse `benchmarks/matrix.py`, `driver.py`, `report.py`, and monitoring; add only what the historical/multi-client runs lack. Correlate actual replay enqueue, producer ack, read-committed Kafka receipt, window finalization, and WebSocket receipt with stable identities that distinguish timestamp ties and duplicates. Keep evidence-only pacing, timing, and reference sorting opt-in; first validate on fresh topics/state without migrating existing deployments. Use a shared time basis or measure/document clock error. Never use historical `timestamp_emit` as transport latency. Track expected-minus-committed and committed-minus-delivered by boundary, counts adjusted for subscriptions, sample sizes, drops, and drain. Export lag, checkpoint timing, backpressure, CPU quotas/utilization/throttling, memory, Kafka/storage I/O where available, and gateway send queues or explicit drop/disconnect counters. Use bounded latency samples and stream comparisons; don't retain the full week in the synthetic driver's in-memory parity maps. Calibrate load generation and telemetry on the same instrumentation settings as scored runs. Check acknowledgement reconciliation, counter resets, usable metrics, actual container caps, and program exit codes. Test missing/duplicate records and missing telemetry to prove the checker fails or marks the run inconclusive. Prefer finalization and first eligibility as distinct timestamps; report event-time/watermark waiting separately. If testing a shorter checkpoint interval for the 1 s goal, compare throughput, visibility, and checkpoint cost, then freeze the chosen configuration for headline runs.

5. **Run full-week correctness and throughput, then a separate live peak test.** In fresh topics, process all seven files with filtering disabled for the coverage run. Check retention against consumer progress and record start/end offsets. Compare committed output on `(symbol, window, type)` against independent EMA/advisory expectations, and reconcile CSV dispositions, publication, accepted trades, and output counts by day/exchange. Measure ingestion, processing, and drain separately. The existing bounded source still emits intermediate watermarks; end-of-input finalization does not recover trades an earlier watermark already excluded. Do not label preload-and-process timing as live or late-induced departures as exact agreement. For the peak test, introduce an explicit capture-time pacing mode (currently `EventEmitter.replayFile` calls `clock.pace(event.eventTimestampMs(), ...)`). Keep exchange event time in the record for Flink; do not overwrite it with capture time. Preserve capture order/gaps and the original CSV ordinal for tie-breaking, disable synthetic gap capping, record missing-capture-time handling, and verify planned vs. actual arrival buckets before measuring the system. Pre-roll enough history to restore initial EMA state, or label the run as cold-state; advance watermarks past the last measured window with unscored trailing input. Run the live pipeline concurrently with the emitter at 1× and 1.25× on the same slice; run three valid replicates per headline condition. Target no sustained backlog growth, exact delivery for the tested subscriptions, and p99 trade enqueue to WS and finalized window to advisory receipt each <= 1 s at 1×. Record signal sample counts; use a controlled rollover test if real peak signals are too sparse, and mark the real-peak advisory p99 inconclusive. Report achieved load, tails, peak backlog, restarts/OOMs, and drain including failed attempts. Save `week-reconciliation`, `oracle-diff`, and `real-peak-runs` artifacts.

   **Agreed full-week acceptance:** Require exact complete-input correctness against the independent oracle. Pilot ordinary bounded replay on a representative slice including known timestamp reversals and the final window. If watermark behavior cannot preserve eligible trades under a practical configuration, use a separately labeled reference run: externally sort all replayable input by the contract event time (source file/row ordinal breaks ties), pass it through the same production query operators under bounded replay, and verify the same input multiset was replayed without precomputing closes or signals. Verify the sort, the last-window output, and zero late exclusions on the slice before scaling up; also check the late-exclusion and oracle-diff gates again for the complete week. Record sorting cost and distinguish replay speed from capture-order throughput. In the live capture-order runs report any differences against the ideal and their causes separately. If only a peak slice was tested in capture order, do not imply the live policy was verified across the full week.

6. **Run a focused scalability and design comparison.** At fixed policies, checkpoint cadence, partition count, hardware, and seed, step achieved load until finding a passing and failing boundary with 1 and 2 TaskManagers at the same per-worker quota; add a fixed-total-budget comparison if worker topology versus aggregate CPU is material. Use coarse exploration, then >=5 measured minutes and three repeats near each boundary (enough sampling to see multiple checkpoints and window rollovers); use longer runs if backlog remains ambiguous. Test uniform versus measured long-tail traffic, then double symbol population and subscriber count independently at a declared baseline passing load, with subscriptions per client and hot-key coverage held explicit. Keep one gateway; distinguish single-client, multi-client, Kafka-only, and gateway-only results. For suspected constraints vary one cap (Flink, Kafka, or gateway) and verify the expected improvement at that stage; otherwise report the observation without attributing cause. For the creative comparison, run identical delayed/duplicate inputs under prompt/drop and grace modes, preserving seed/schedule; report advisory misses/extras against ideal truth, finalization delay, and managed state/resource cost. Include a live annotated chart showing how each real marker relates to the two EMA values and triggering window.

   **Capacity rule:** pre-register target definitions and thresholds before the scored runs. Use at least 98% achieved/paced input for synthetic steps (and check the arrival trace for historical steps), correct observed output after drain, and no sustained growth in producer/Kafka/Flink/gateway backlog. As a concrete initial slope check, compare checkpoint-aligned medians over the last three post-warmup measurement blocks of at least 60 s; flag consecutive increases larger than one normal checkpoint batch and inspect the raw series for producer stalls, skew, and checkpoint batching. Report throughput from the steady window separately from delivery including drain; give `highest passing / first failing` and replica spread, not a point beyond the measured range. If the generator cannot achieve target or required telemetry is missing, the run cannot establish that pipeline limit. A 1.5× worker-capacity gain is a project stretch check only when Flink is shown to be the limiting stage; report measured headroom and any downstream ceiling without claiming linear scaling.

7. **Package facts and perform a claim audit.** Put sanitized report-ready evidence under `experiments/report-ground/` (proposed), with durable links and hashes for bulky local artifacts instead of checking in the dataset, logs with secrets, or raw broker data. Include `index.md`, `claims.csv`, `runs.csv`, semantic/architecture notes, source citations, compact data tables/plots, and a team record. Each claim row must specify rubric criterion, exact claim, metric/unit/denominator, scope, run IDs, source revision/config and dataset IDs, artifact path or URL plus row/figure locator, uncertainty or limitation, and reviewer. Every run retains command, inputs, seed, host/container versions, effective caps, monitoring settings, timing/sampling method, output/metrics, and status (`pass`, `fail`, `inconclusive`). Keep the final version reproducible from a public repo link and a pinned revision; after code or configuration changes, rerun affected validations or scope the old numbers explicitly to the old revision. Have a teammate reproduce a small fixture and regenerate at least one table/plot from indexed source artifacts. No unsupported claim is marked ready.

## Rubric handoff checklist

| Criterion | Minimum evidence to attach to the report ground |
|---|---|
| Functionality | Reviewed spec, independent oracle and fixture, per-window full-week diff for both queries, real subscription test and live advisory capture. |
| Performance | Seven-day counts and timings; real-time peak repeats with achieved load, latency distributions, lag, drain, and completeness. |
| Scalability | Real exchange mix and rank curve; passing/failing capacity bounds and repeats for resource changes; headroom, symbol growth and subscriber results with bottleneck evidence. |
| Creative explorations | Matched policy comparison with correctness/latency/state trade-offs, decision rationale, and live explanatory chart. |
| System design and architecture | Validated diagram from CSV/producer through keyed Kafka/Flink, state, watermarks, checkpoints and committed Kafka to WebSocket; design rationale and scaling bounds. |
| Implementation explanation | Raw-field-to-action table, worked EMA/crossover trace, metadata use vs. fields merely present, config/runtime/hardware and code pointers pinned to the measured revision. |
| Evaluation and performance | Regenerable correctness table, measured capacity/latency and CPU/memory figures, real long-tail analysis and controlled sweeps; limitations, invalid runs, and no GPU use if confirmed. |
| Academic writing | Evidence-to-section map for abstract, introduction/dataset, architecture, implementation, evaluation, conclusion; cited dataset and sources, figure captions with units/config, ACM 4–5 page and public-link preflight for the writer. |
| Individual contributions | Each member provides the rubric's three responses: important decisions, challenges, and specific contribution plus team-functionality reflection, backed by commits/reviews/run IDs where available. |
| Teamwork | Review log and ownership, shared data/run manifests, cross-review or reproduction record. Use the brief's individual-work exception only if applicable. |

**Release gate:** Prioritize the data manifest, oracle/live Query 2, and full-week run before extra experiments. If storage, data access, latency, correctness, or reproducibility prevents a headline claim, record what was tested and the precise blocker. A partial run is not a full-week pass, eventual parity is not sustainable capacity, and a failed target cannot be repaired by report wording.

**Writer handoff:** Provide one compact table for full-week coverage and oracle errors, one figure for real workload shape, and one multipanel figure for sustainable throughput, p99, and CPU/memory across configurations. Link the full run ledger and secondary evidence instead of squeezing each experiment into the paper. For each headline result, give the strongest supported sentence and its necessary qualification (e.g. exact on reference replay, peak slice only, or gateway-only). Do not claim Exceptional where a required result is still missing.
